# 0037. Every user pairs their own machine, and the bridge signs machine tokens with Ed25519

- Status: accepted (devil: PROCEED-WITH-CONDITIONS, 2026-10-31; amends C21 of the osionos verdict `docs/ide/vscode-backend/devil-verdict-2026-10-30.md`)
- Date: 2026-10-31
- Deciders: devil (ruling), owner (lives with it)

## Context

- The owner's rule (2026-10-31): users connect their own machines, the way VS Code does. The bridge brokers identity, pairing and presence only.
- Today the node verifies `osionos_ide1` with the bridge's shared IDE secret and one fixed owner (`packages/osionos-node/cli.mjs:56-58`). Handing that secret to a second user would let them forge tokens for every user.
- C21 blocked Stage 1 for anyone but the owner.
- The plan is osionos `docs/ide/vscode-backend/own-machines-plan.md` (branch feat/vscode-backend). It has device-code pairing, bridge-signed `osionos_mc1` tokens, a heartbeat on public routes (Funnel) and `public.osionos_machines` under RLS.
- The `NODE_ID` regex (`scripts/ide-token.mjs:35`) admits names any user picks, such as `laptop`.
- Behind Funnel the pairing start limit is one global key (`scripts/ide-relay-pairing.mjs:9,51`).

## Decision

- **Tokens:** Ed25519 machine tokens, signed by the bridge and verified offline by the node against a pinned, `kid`-indexed key set.
- **Stage 1 for owners:** allowed for the owner of a machine. C21 now reads: "BLOCKED for any machine the viewer does not own".

## Alternatives considered

- **Hand out the shared HMAC secret:** any node could forge tokens for any user. Rejected.
- **Per-machine HMAC secrets:** the bridge stores N secrets and the node can mint for itself. Asymmetric removes both.
- **Keep Stage 1 owner-only:** contradicts the product rule.

## Consequences

- The ten conditions in the plan's "Devil verdict 2026-10-31" are the acceptance criteria:
  - C21 amended;
  - `aud`, `kid` and `jti` on tokens;
  - key rotation through a heartbeat-delivered next key;
  - a local account confirm against code phishing and hijack, with a global claim cap;
  - a signed loopback identity challenge before any token is posted;
  - heartbeat ts monotonic and an `ideOrigin` parse;
  - revocation from Postgres, with live sockets closed on a 410;
  - machine ids generated by the bridge;
  - the Funnel start-limit DoS named;
  - `osionos_ide1` retirement tracked.
- Condition 4 (phishing) must hold before Phase 3/6 lift the loopback-only `ideOrigin`. The loopback limit is what bounds that risk today.
- Caveat: the phishing analysis assumes `ideOrigin` stays loopback. A non-loopback origin turns an approved attacker machine into a place where the victim types secrets.

## Residuals accepted (security review, 2026-10-31)

- **Claim lockout lever:** the global failed-claim cap (500 per 10 min) lets a few hundred accounts failing on purpose stop every user from claiming for 10 minutes. It is sized so this needs many accounts; brute force over 20^8 codes stays out of reach (`scripts/bridge-machines-pairing.mjs`).
- **Per-process limits:** the pairing, claim and heartbeat limiters and the approve queue live in one bridge process. A restart forgives them. Two replicas would each grant their own budget.
- **Funnel start limit (condition 9):** without a client-IP header, every start shares one key, so one caller can stall pairing for all users. That is the safe direction.
- **Cookie port on a multi-user host:** the loopback node cookie drops `__Host-` (ADR 0036). Another local user who can bind the same loopback port first could receive it. Phase 1 is a single-user laptop. A shared host needs a per-user port check before it ships.
- **jti after a restart:** the node's used-jti set is in memory, so a restart reopens the replay window. The token's 900 s life bounds it.
- **Retiring `osionos_ide1` (condition 10):** https://github.com/Univers42/osionos/issues/238.
