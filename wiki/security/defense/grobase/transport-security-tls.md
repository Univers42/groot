# Transport Security / TLS — grobase (the BaaS backend)

> Every byte of API traffic between a client and the grobase backend is encrypted: a ModSecurity
> nginx WAF terminates TLS 1.2/1.3 exclusively, presents a certificate delivered via Docker secrets
> (never baked into the image), and forces browsers to pin HTTPS permanently via a two-year HSTS
> header injected by Kong's response-transformer plugin.

## What it is (the concept)

**Transport Layer Security (TLS)** is a cryptographic protocol that establishes an encrypted,
authenticated channel between two endpoints before any application data is exchanged. A correctly
deployed TLS stack prevents passive eavesdropping, active man-in-the-middle interception, and
**protocol-downgrade attacks** that attempt to negotiate a weaker cipher or older protocol version.
**HTTP Strict Transport Security (HSTS)** is a response header that instructs the browser to
refuse plain HTTP connections to the same origin for a defined period, closing the **SSL-stripping**
window that exists only on a user's very first visit.

## What it defends against

See [Man-in-the-Middle & Protocol Downgrade](../../attack/transport-security-tls.md).

In the grobase context the threat is concrete: the Kong gateway exposes its admin API internally
and routes every authenticated API call — including the `JWT_SECRET`-signed bearer tokens that
authorize database queries, storage operations, and realtime subscriptions. Any cleartext path or
negotiated-downgrade to TLS 1.0/1.1 would let a network-adjacent attacker capture those tokens
and impersonate any tenant. An SSL-strip attack on a returning user's browser session could
silently redirect API calls over HTTP before the authenticated session cookie is sent.

## How grobase implements it

**Single public listener, TLS-only.** The WAF service is the sole container that publishes ports
to the host; Kong's HTTP port 8000 is bound to `127.0.0.1` only. The nginx configuration at
[`apps/grobase/infra/docker/services/waf/conf/nginx.conf`](../../../../apps/grobase/infra/docker/services/waf/conf/nginx.conf)
makes this explicit:

```nginx
# This is the ONLY public-facing listener; Kong's :8000 becomes internal.
listen 443 ssl http2;
ssl_certificate     /run/secrets/localhost_cert;
ssl_certificate_key /run/secrets/localhost_key;
ssl_protocols       TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;
```

Lines 3 and 15 enforce the protocol floor: `ssl_protocols TLSv1.2 TLSv1.3` causes nginx to
reject any handshake that cannot negotiate at least TLS 1.2, eliminating SSLv3, TLS 1.0, and
TLS 1.1.

**Certificate delivered as Docker secrets, not bind-mounted files or image layers.**
[`apps/grobase/docker-compose.yml`](../../../../apps/grobase/docker-compose.yml) declares the
TLS material as named secrets sourced from the `certs/` directory (generated by `make certs`
via `scripts/certs/generate-localhost-cert.sh`):

```yaml
# TLS material for the waf delivered as Docker secrets, not bind mounts.
secrets:
  localhost_cert:
    file: certs/localhost.pem
  localhost_key:
    file: certs/localhost-key.pem
```

[`apps/grobase/orchestrators/compose/base/gateway.yml`](../../../../apps/grobase/orchestrators/compose/base/gateway.yml)
mounts these secrets onto the WAF service so the private key is available at `/run/secrets/localhost_key`
inside the container and never appears in an image layer or a bind-mount path visible to other
containers:

```yaml
secrets:
  - localhost_cert
  - localhost_key
```

**HSTS enforced globally via Kong's response-transformer plugin.**
[`apps/grobase/infra/docker/services/kong/conf/kong.yml`](../../../../apps/grobase/infra/docker/services/kong/conf/kong.yml)
injects the header on every response through the global `response-transformer` plugin (line 77):

```yaml
- Strict-Transport-Security:max-age=63072000; includeSubDomains; preload
```

`max-age=63072000` is exactly two years. `includeSubDomains` covers every subdomain, and
`preload` signals eligibility for browser preload lists. The same plugin removes the `Server`,
`X-Powered-By`, and `Via` headers that would otherwise disclose Kong's version and nginx's
identity to an attacker probing the stack.

## How we know it is applied

The milestone gate
[`apps/grobase/scripts/verify/m140-network-controls.sh`](../../../../apps/grobase/scripts/verify/m140-network-controls.sh)
proves the WAF is the active sole public listener through two non-vacuous arms:

- **ARM A** — sends an SQLi probe, an XSS probe, and a path-traversal probe through the public
  WAF endpoint and asserts each returns HTTP 403 from the OWASP CRS. A benign request to
  `/waf-health` must return 200 and a benign real route (`/data/v1/health`) must not be 403,
  proving the WAF passes legitimate traffic rather than blocking everything. A **negative
  control** sends the same SQLi directly to Kong (bypassing the WAF) and asserts it does
  *not* return 403, attributing the block to the WAF/CRS layer specifically.
- **ARM B** — stands up an isolated network topology and proves via raw TCP socket exit codes
  that the public-edge container (`kong`) cannot reach `postgres:5432` on the data-plane
  network, while the legal front-door (`query-router`) can. This confirms the WAF/Kong edge
  has no direct path to the engines even if TLS were somehow bypassed.

The gate is included in the grobase milestone battery and must pass before any network-hardening
change is considered done. The waf service healthcheck in `gateway.yml` (line 19) additionally
verifies the listener is up on every `docker compose` start.

## Reference

The [Transport Layer Security Cheat Sheet — OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)
defines the authoritative minimum requirements for TLS configuration in server-side applications,
including protocol version floors, cipher suite selection, certificate management, and HSTS
deployment. The grobase configuration directly implements the cheat sheet's requirements to
disable TLS 1.0/1.1, prefer TLS 1.3 where available, and deploy HSTS with long `max-age` and
the `preload` directive.

This control maps to **OWASP Top 10 A02:2021 — Cryptographic Failures**, which covers exposure
of sensitive data in transit when encryption is absent, weak, or misconfigured.

## Residual risk / assumptions

**Local CA, not a public CA.** In the default (`make certs`) setup the certificate is signed by
a locally generated CA trusted via `scripts/certs/trust-localhost-cert.sh`. A production
deployment must replace the certificate and key with material issued by a publicly trusted CA
before exposing the stack to the internet; the Docker secrets mechanism is CA-agnostic and
requires no code change to do so.

**HTTP port 80 is published by the WAF.** The nginx configuration listens on both 80 and 443
(line 6 of `nginx.conf`). The `ssl_protocols` directive applies only to TLS connections on 443;
port 80 accepts plain HTTP. There is no nginx-level redirect from 80 to 443 in the current
configuration. HSTS prevents the browser from following a plain-HTTP URL on a return visit, but
only after the first HTTPS contact has been made. A first-time visitor navigating to the HTTP
port directly will not be protected by HSTS.

**Internal service-to-service traffic is not TLS.** All communication between Kong and upstream
services (PostgREST, GoTrue, the Rust data plane, etc.) is plain HTTP over the internal Docker
bridge network `mini-baas`. This is a trust-network assumption: container-to-container traffic
on a single host's bridge network is not routable from outside the host, but a compromised
container on the same network could eavesdrop on inter-service calls.

**Kong Admin API.** The Kong Admin API is not published to the host (`gateway.yml` line 40–44);
it is reachable only from within the `mini-baas` network so Prometheus can scrape it. A
compromised container on that network could call the admin API and retrieve declarative config
including credential placeholders (already substituted at runtime by the entrypoint `sed`).
